# Generic trust ports (local implementation)

The `integration::eligibility` and `integration::attempt_store` modules implement the reviewed GE-TRUST pure library slice. They do not authenticate a real identity service, inspect Git objects, publish hosted checks, issue credentials, or provide durable storage. A test-only trusted-controller integration fixture is documented in [trusted-controller-fixture.md](trusted-controller-fixture.md). It does not supply production authentication; an authoritative hosted gate still requires its own reviewed authority adapter and protected controller. Existing native engine reports, verdicts, CLI behavior and schemas are unchanged.

## Protected construction and inputs

Only a protected controller may construct `EligibilityPolicy`, choose the `AuthorityProvider`, supply the trusted UTC Unix-second `now`, resolve artifact references to bounded bytes, advance generations, append records or publish pointers. These Rust interfaces are not a process security boundary: arbitrary code implementing a dishonest provider or directly constructing an attempt record can lie. Do not deserialize candidate-provided configuration into the protected policy, load providers from candidate code, or expose store mutation to analyzers. Existing `load_envelope_json` and `verify_engine_artifacts` enforce the integration byte/structure/recomputation budgets; artifact URIs are never fetched by this API.

`EligibilityPolicy` freezes the exact full `RunBinding` (including repo/task/worktree/requirements, candidate/base/merge group, snapshot and baseline), producer and analyzer versions, sorted required scopes, exact contract-byte SHA-256 digest, requested action, authorized producer principals and required approval purposes with per-purpose authorized principals. Principal strings are exact provider-qualified identifiers (for example an issuer plus subject encoded by the adapter); the adapter must prevent ambiguous/colliding identities. Nonempty protected producer allowlists are mandatory. Every declared approval purpose requires a nonempty principal allowlist. Authentication alone confers no authorization.

Call `evaluate_eligibility(&envelope, ArtifactBytes { contract, facts, report }, &policy, &provider, now, cause)` on every use. It validates the engine-backed envelope, matches immutable policy expectations, verifies exact supplied artifact bytes and recomputes the full technical report internally. There is no `evidenceVerified`/`trusted` input. Native-only profiles fail this stronger gate. Error/cancellation return execution failure; complete technical BLOCK remains blocked; partial evidence remains incomplete and can never be repaired by approvals. `technical_decision` is present only after successful artifact recomputation, including verified partial/BLOCK evidence. Eligibility never mutates the envelope or report.

## Authentication, authorization and freshness

`AuthorityProvider::verify_producer` authenticates a producer record bound to the supplied envelope and canonical digest. `verify_approval` resolves an opaque reference to a freshly authenticated record. The provider must check signatures/issuer or its reviewed equivalent, prevent substitution, and obtain current revocation state; unavailable authority returns `AuthorityError::Unavailable`. Typed records deliberately do not implement `Deserialize` and contain no trusted boolean. Fixtures implementing this port are confined to the tests and are not a production provider choice.

The evaluator independently checks producer identity, canonical envelope digest, authorized principal and validity. For REQUIRE_APPROVAL, each protected purpose must have a referenced record with an allowed principal, exact action, full binding and protected contract digest. Unknown purposes, invalid/unauthorized records and unavailable responses deny, even when another reference would otherwise suffice. Duplicate approvals for one purpose cannot satisfy another. Empty purpose policy never grants REQUIRE_APPROVAL. ALLOW still requires producer authentication/authorization; it does not require approvals. References are consulted only for REQUIRE_APPROVAL.

Authority time windows use signed `i64` UTC epoch seconds with `issued_at <= now < expires_at`; revoked records always deny. Envelope finish must be at or before `now`, and a nonnull expiry must be strictly after `now`. RFC3339 fractional seconds are compared at nanosecond precision against the whole-second trusted clock, so future fractional finishes are not rounded down. Null envelope expiry supplies no TTL, but never bypasses producer/approval expiry, revocation, policy comparisons or artifact verification. The provider must not return cached authority past its freshness guarantee; this library supplies no authority cache. A prior eligible result or published current pointer never substitutes for reevaluation.

## Digests and immutable history

The canonical envelope digest is SHA-256 of compact `serde_json::to_vec` of the validated typed envelope. This uses the existing declaration order and sorted set requirements, preserves diagnostic/rule order, and is a local Rust integration convention, not a newly claimed cross-language canonical JSON standard. Artifact digests always hash exact supplied bytes.

`EligibilityPolicy::content_digest()` hashes compact Serde JSON of the two-element tuple `("guard.eligibility/v1alpha1", policy)`. This includes full binding, producer, scopes, exact contract digest, action and authorization policy. Struct fields use declaration order; `BTreeMap`/`BTreeSet` entries are sorted. Set-like binding/scope vectors must already have the valid sorted representation. Equivalent protected inputs have the same work key; changed authorization/configuration gets a different key. Run IDs remain unique attempts and are not work keys. A canonicalization change requires an explicit version change and review.

`Target` partitions history by repo ID, task ID and sorted unique nonempty requirement IDs. The protected controller calls `advance(target, expected_generation, content_digest, run_id)` *before* running a new attempt, including a recheck of identical inputs. The generation compare-and-set rejects a stale expected generation, globally reused run ID or malformed key. Generation zero denotes a target with no registered attempts. Successful advance registers that exact target/key/run ID at the next generation and clears the current pointer immediately; unfinished or failed rechecks therefore cannot expose the previous PASS as current.

`append` accepts only a registered run with matching target, key and generation. Every accepted attempt is immutable: identical replay returns `IdenticalReplay`, conflicting content under a run ID returns `Conflict`. Old generations may finish and append to their original history. `publish(run_id)` succeeds only for an appended record at the target's active generation; its registered key and target were checked at append. A late old PASS cannot replace a newer FAIL, even for the same binding/work key. Repeated publication of the same current attempt is idempotent. `history` returns original append order; no deletion/update method exists.

`InMemoryAttemptStore` demonstrates this algorithm under exclusive Rust `&mut` access. It is not durable, restart-safe or cross-process CAS. A real implementation must atomically persist generation registration, pointer invalidation, append collision detection and conditional publication, maintain uniqueness across clients, and reconcile uncertain mutations before retry. The controller must persist/query generation state in its chosen backend. No database, lock service or retention duration is selected here. The stored `eligible` value is historical and must not be used as cached authority.

## Minimal audit and operating obligations

`EligibilityResult.audit` serializes a fixed outcome code, SHA-256 identifiers for a verified producer and verified approvers, requested action/purposes, binding, protected content, envelope, optional causal predecessor, and trusted timestamp. Actor identity is recorded only after authenticated producer binding/validity checks; unauthorized but authenticated producers can be audited as such. Approver identifiers are included after all supplied records validate. Hashing identifiers reduces accidental disclosure; hashes are neither encryption nor anonymous, especially for enumerable identifiers. Full artifact references/digests and approvals remain bound through the immutable envelope digest and retained evidence.

No arbitrary provider error, source excerpt, diagnostic message, path, credential or free-form causal text is copied into audit output. Fixed denial codes intentionally do not repeat provider secrets. The controller must keep a protected mapping from identity digests to verified principal records when human-readable attribution is needed, enforce tenant-specific audit/evidence access and retention/deletion requirements, redact upstream diagnostic artifacts, protect the trusted clock and policies, and preserve causal links to immutable records. This API neither invents a retention duration nor treats filesystem permissions as identity authentication.

## Evidence and limitations

`tests/integration_eligibility.rs` exercises valid fixture authority and unauthorized/untrusted/unavailable records, every binding dimension, exact-byte revalidation, complete/partial/error/cancelled decisions, approval-purpose/action/scope checks, expiry/revocation and audit minimization. `tests/integration_attempt_store.rs` exercises same-binding late PASS versus FAIL, early recheck invalidation, repo/task/requirement isolation, registered key/generation constraints, collisions and identical replay. These are generic fixture tests, not a real hosted-controller integration or evidence that any provider/issuer is trusted in production.
